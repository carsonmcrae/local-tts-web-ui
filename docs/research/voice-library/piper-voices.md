# Piper voices: catalogue, engine, quality evidence

Read-only web research for TTSNative. All facts read 2026-10-21 unless stated. Labels: **documented** (URL read), **claimed** (stated by a secondary source, a search-engine snippet, or the publisher of the data about itself), **inference** (my reading). Everything read on the web was treated as untrusted data. This is not legal advice.

Method: `voices.json` (resolve URL) for the voice list, sizes and MD5; the Hugging Face "raw" LFS pointer for each `.onnx` for the SHA-256 (voices.json carries MD5 only); each voice's `MODEL_CARD` (no `.md` extension) and selected `.onnx.json` configs; then the dataset pages the cards cite. Hosts that refused connections or were down today: `www.cstr.ed.ac.uk` (Lessac/Blizzard licence page), `festvox.org` (CMU ARCTIC), `ast-astrec.nict.go.jp` (Hi-Fi-CAPTAIN, "maintenance" redirect), `datacat.liverpool.ac.uk` (ARU corpus), `community.home-assistant.io` (403), `web.archive.org` (blocked by the fetch tool). Where that happened the licence is marked **claimed** from a search snippet or a secondary page.

## 1. Answer

No English Piper voice reaches verdict **A** on its own terms except **en_US-bryce-medium**, whose speaker (Bryce Beattie) recorded his own voice, published the model as public domain and wrote "This is my voice", "Feel free to use these for any legal and ethical purpose" and "If somebody wants to upload these to HuggingFace or somewhere similar, you have my blessing" (documented, brycebeattie.com). The reference case **de_DE-thorsten-\*** (all four tiers) is also **A**: CC0 dataset plus Thorsten Müller's own statements ("I contribute my voice as a person believing in a world where all people are equal"; website: "gave his voice to the public – voluntarily!", "Private, school, club or commercial use"). Both carry a lineage caveat: every medium-tier English voice except kristin, norman, ljspeech, cori and lessac itself was **fine-tuned from en_US-lessac-medium** (and thorsten-high from lessac-high; every low-tier voice from en_US-ryan-low), and the Lessac/Blizzard 2013 data is licensed non-commercial/"Research Purposes" (claimed; the licence page was unreachable today) while RyanSpeech is CC BY-NC-ND per its own paper; whether fine-tuned weights inherit those terms is undetermined (the Piper maintainer: "I have no idea how licenses are supposed to apply in the context of machine learning"). Verdict **B** (permissive licence, no documented speaker authorization): joe, john, kristin, norman, ljspeech-{medium,high}, libritts-high, libritts_r-medium, kathleen-low, sam, arctic (licence text unverified), and the en_GB voices alba, aru, cori-{medium,high}, jenny_dioco (custom attribution terms), northern_english_male and southern_english_female (CC BY-SA), vctk. Verdict **C** (restrictive, non-commercial, "see URL"/unverifiable, or research terms): lessac-{low,medium,high} (Blizzard non-commercial), ryan-{low,medium,high} (CC BY-NC-ND/SA), hfc_female and hfc_male (CC BY-NC-SA 4.0), l2arctic (CC BY-NC 4.0), semaine (CC BY-NC-SA 4.0), amy-{low,medium}, danny-low, kusal-medium and alan-{low,medium} ("See URL" pointing at Mycroft repos whose dataset licence is not stated; the apope_low model LICENSE reads "Copyright 2022 Mycroft AI / All Rights Reserved"), mike-medium (card says CC0 at OHF-Voice/voice-datasets, but that repo has no "mike"), reza_ibrahim-medium (card says CC0; the cited dataset page has no licence and no card; bilingual Quran recitation whose narrator's permission is undocumented). Engine: the ONNX contract is fully documented in the archived **MIT** rhasspy/piper code (inputs `input` int64 [1,N], `input_lengths` int64 [1], `scales` float32 [3] = noise_scale, length_scale, noise_w, optional `sid` int64 [1]; output `output` float32 with audio in the last dimension; ids = BOS `^`(1) then each phoneme id followed by PAD `_`(0), then EOS `$`(2); phonemes = espeak-ng IPA codepoints, NFD-normalised, language-switch flags stripped, clause punctuation re-inserted from the terminator), so a voice **can** be run from plain onnxruntime plus an espeak-ng IPA phonemiser without any GPL Piper code (piper1-gpl is GPL-3.0; piper-tts 1.1.0/1.2.0 on PyPI are MIT, 1.3.0 onward GPL-3.0-or-later). The caveat is espeak-ng itself: GPL-3.0-or-later, and Piper's sentence/punctuation handling depends on `espeak_TextToPhonemesWithTerminator`, which piper1-gpl says is now in upstream espeak-ng.

### ONNX inference contract (documented from code)

MIT reference: `rhasspy/piper/src/cpp/piper.cpp` and `src/python_run/piper/voice.py`; identical in GPL `piper1-gpl/src/piper/voice.py`.

- Inputs (`// From export_onnx.py`): `{"input", "input_lengths", "scales", "sid"}`. Shapes: `phonemeIdsShape{1, N}`, lengths `{1}`, scales `{3}`, speaker id `{1}`; Python: `np.array(phoneme_ids, dtype=np.int64)` expanded to (1,N); `input_lengths` int64 (1,); `scales` = `[noise_scale, length_scale, noise_w_scale]` float32; `sid` int64 added only when a speaker is set (`if (synthesisConfig.speakerId)`; GPL code: when `num_speakers > 1`, falling back to `default_speaker_id`).
- Output: name `"output"`; C++ reads `audioCount = audioShape[audioShape.size() - 1]` (audio in the last dimension); MIT Python `session.run(None, args)[0].squeeze((0, 1))` -> shape (1,1,T) float32 (inference from the squeeze); GPL code `result[0].squeeze()` and, in newer exports, `result[1]` alignment lengths scaled by `hop_length` (optional). Int16: MIT normalises to peak, `audio_norm = audio * (max_wav_value / max(0.01, np.max(np.abs(audio))))` then clip/cast; C++ identical with `MAX_WAV_VALUE = 32767.0f`; GPL default `normalize_audio=True` with the same rule, else clip to [-1,1] * 32767.
- Config JSON fields read (GPL `config.py`, documented): required `num_symbols`, `num_speakers`, `audio.sample_rate`, `espeak.voice`, `phoneme_id_map`; optional `phoneme_type` ("espeak" | "text" ...), `speaker_id_map`, `piper_version`, `inference.noise_scale/length_scale/noise_w`, `hop_length`, `default_speaker_id`, `vowel_clusters`. Example (lessac-high): `audio {sample_rate 22050, quality "high"}`, `espeak {voice "en-us"}`, `inference {noise_scale 0.667, length_scale 1, noise_w 0.8}`, `phoneme_type "espeak"`, `phoneme_map {}`, `phoneme_id_map` 154 entries mapping a codepoint string to a 1-element int list (`"_":[0]`, `"^":[1]`, `"$":[2]`, `" ":[3]`, `"æ":[39]`...), `num_symbols 256`, `num_speakers 1`, `speaker_id_map {}`, `language {code "en_US", ...}`, `dataset "lessac"`.
- Phoneme ids (documented, `piper-phonemize/src/phoneme_ids.hpp/.cpp` and GPL `phoneme_ids.py`/`const.py`): `PAD = "_"  # padding (0)`, `BOS = "^"`, `EOS = "$"`; config flags `interspersePad = true`, `addBos = true`, `addEos = true`. Rule: emit BOS ids; (GPL code also emits one PAD after BOS); for each phoneme codepoint, emit its ids then PAD ids; unknown phonemes are skipped and counted/logged; finally EOS ids. MIT Python: `ids = list(id_map[BOS])`, per phoneme `ids.extend(id_map[phoneme]); ids.extend(id_map[PAD])`, then `ids.extend(id_map[EOS])`.
- Text -> phonemes (documented, `piper-phonemize/src/phonemize.cpp`, GPL `espeakbridge.c` + `phonemize_espeak.py`): `espeak_Initialize(AUDIO_OUTPUT_SYNCHRONOUS, 0, data_dir, 0)`; `espeak_SetVoiceByName(voice)` with the config's `espeak.voice`; loop over `espeak_TextToPhonemesWithTerminator(&text, espeakCHARS_AUTO, espeakPHONEMES_IPA /* 0x02 */, &terminator)`; `terminator & 0x000FFFFF` decoded to `.`, `?`, `!`, `,`, `:`, `;` and appended as phoneme characters (comma/colon/semicolon followed by a space); sentence ends when `(terminator & CLAUSE_TYPE_SENTENCE) == CLAUSE_TYPE_SENTENCE`; output NFD-normalised (`una::norm::to_nfd_utf8` / `unicodedata.normalize("NFD", ...)`), split into single codepoints, and language-switch flags `(...)` removed. Arabic voices get `tashkeel` diacritisation first. So the model consumes one id per _Unicode codepoint_ of IPA (stress marks, length marks and combining marks are separate ids).
- Running without GPL Piper code: feasible (inference). Needed: onnxruntime; the voice's `.onnx.json`; an espeak-ng phonemiser producing IPA (`espeakPHONEMES_IPA`) for the config's voice name; the BOS/PAD/EOS interleave above; sentence splitting and punctuation re-insertion. With plain `espeak_TextToPhonemes` (no terminator variant) you lose espeak's clause-type signal and must reinsert punctuation yourself (inference); upstream espeak-ng at the pinned commit provides `espeak_TextToPhonemesWithTerminator` (documented via BUILDING.md). espeak-ng remains GPL-3.0-or-later regardless.

### Text normalisation

- Piper has no English normaliser. MIT C++ and Python pass raw text to espeak-ng; GPL `phonemize_espeak.py` contains "no logic for converting numbers to words" (documented); the GPL changelog never mentions normalisation; `unicode-rbnf` appears only in the `zh` and `th` extras (documented, PyPI requires_dist). Numbers, dates, abbreviations and currency are therefore whatever espeak-ng's `TranslateNumber()` and dictionary rules produce: "The operation the `TranslateNumber()` function is controlled by the language's `langopts.numbers` option"; `_dpt` "Word spoken for the decimal point/comma"; `$abbrev` "Speak the word as individual letters, even if it contains a vowel" (documented, espeak-ng docs/dictionary.md).
- Open/closed issues (documented, issue search pages): rhasspy/piper #54 "Feature: Support abbreviations" (open, 2023), #63 "Loss of punctuation and unable to read the numerical letters" (open), #78 "Preprocessing step (feature request)" (closed), #536 numbers differ after fine-tuning (open), #747 "Incorrect Number Pronunciation in Piper VITS with eSpeak-NG" (open, 2025); piper1-gpl #317 "English: years read as cardinals (1975 -> "nineteen hundred and seventy-five")" (closed Oct 2026), #267 Polish cardinals (open), #135/#136 Roman numerals (closed). Maintainer in #271: most voices use an espeak-ng phonemizer that "has a GPL license" (documented).

## 4. Quality evidence (all claimed/anecdotal unless marked)

- **No controlled Piper-vs-Kokoro listening test found.** CodeSOTA's comparison page: "this page does not claim a measured naturalness or latency winner"; earlier Kokoro-winner rows withdrawn because manifests "contain placeholder hashes"; "A separate preference study cannot replace a matched Piper-versus-Kokoro test using the same device, prompts and voices." (documented quotes from a secondary site).
- **TTS Arena**: the 2024 launch lineup (ElevenLabs, MetaVoice, OpenVoice, Pheme, WhisperSpeech, XTTS) did not include Piper, and no search result shows Piper on the official TTS-AGI arena (search-level finding). tts.ai's own scores (Kokoro 4.8/5, Piper 4.15/5) are that site's internal numbers, not an arena (claimed).
- offlinetts.com "Browser TTS Showdown" (claimed, search snippet): "informal A/B tests with 20 listeners", MOS estimates Kokoro 4.3-4.5 vs Piper 3.8-4.0; Piper "occasionally sounded robotic on longer passages"; the page itself calls its grades "catalog aids, not standardized MOS results".
- PromptQuorum (claimed, "community impressions"): Piper "somewhat more robotic", Kokoro "noticeably more human"; Piper runs on a Raspberry Pi.
- mustafa.net six-month production review (documented, blog): preferred en_US-amy-medium ("sounded natural enough that automation responses didn't feel robotic or uncanny"); en_US-lessac-medium "sounded noticeably worse than what I remembered from Amy. Harder consonants, less natural phrasing"; weaknesses "Less emotional inflection, occasional weird prosody, less natural phrasing"; speed on a 2-vCPU VM: 10-word sentence 150-250 ms, single-threaded, 200-300 MB RSS; an upstream rename of voice models caused downtime.
- Home Assistant forum: tag page lists "Collections of Pre-trained Piper Voices" (32 replies, ~24k views, active Aug 2026) but the forum returned 403 to the fetcher; a HA add-on PR added en_GB-cori-high/medium (documented, github.com/home-assistant/addons/pull/3688 via search). No forum consensus on a "best" English voice could be read today.
- Raspberry Pi speed: Piper's own claim is only "optimized for the Raspberry Pi 4" (documented); Snapcraft listing "around 95% realtime on Pi 4" (claimed); a Pi 5 guide reports RTF ~0.19 (claimed). No controlled benchmark found.
- Long-form weaknesses are consistently described as flat/robotic prosody and occasional odd phrasing (claimed, several sources); VITS-specific artefacts were not specifically documented in what I read. Multi-speaker models: "Multi-speaker models can quickly switch between different speakers," but a single speaker may sound lower in quality than in a single-speaker model (documented, piper-samples page).
- Community "best voice" mentions found: amy-medium (one blog), cori-high (added to HA add-on on request), lessac (the docs' default example, not a quality claim). Nothing found for ryan or hfc beyond their presence.
